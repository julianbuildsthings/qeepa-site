# Product

## Platform

web

## Users

Photographers who shoot RAW and edit their own keepers. The situation is a
finished shoot sitting in a folder on a Mac or an external drive: hundreds or
thousands of frames, each often existing several times over as a RAW negative,
a JPEG, and an edited working file. The job is deciding which frames survive,
and doing it quickly enough that culling stops feeling like a chore.

This is a single-user desktop tool. There are no teams, no collaborators, and
no accounts.

## Product Purpose

Qeepa is a local-first desktop photo manager for browsing, comparing, rating
and tagging large folders of photos without importing or copying anything. It
reads a folder directly off disk and presents what is actually there.

Success is a photographer getting through a shoot faster and with more
pleasure than their current tool allows, while keeping full authority over
what stays and what goes.

## Positioning

Three mechanisms a neighbouring product could not truthfully copy without
rebuilding itself:

- **The filesystem is the source of truth.** No import step, no managed
  library, no copying or moving. The gallery is generated by scanning the
  folder each time it is opened, so what is shown is what is on disk now. The
  local SQLite database is a cache only; deleting it loses nothing.
- **Tracks.** Files sharing a filename stem — RAW, JPEG, and working files
  such as `.afphoto` — are grouped automatically into one logical shot with
  switchable tracks, across roughly 29 recognised RAW extensions.
- **Ratings live in the photos' own neighbourhood.** Stars and tags are read
  from and written to `.xmp` sidecars using Lightroom's conventions, reading
  both the `photo.xmp` and `photo.ext.xmp` naming schemes. Ratings other tools
  wrote are recognised; ratings Qeepa writes are immediately visible in those
  tools. Nothing is trapped in a proprietary format.

## Operating Context

Qeepa is used alongside an existing photo workflow, not in place of one —
Lightroom, FastRawViewer, Affinity Photo, and Finder. Shoots live as folders
on local or external drives. Culling is keyboard-driven and done in long
sessions. Sharing hands real files to the macOS share sheet, optionally
bundling the `.xmp` sidecar alongside the image.

## Capabilities and Constraints

**Confirmed shipped, end to end:** folder scan into shoots; gallery grid and
single-photo detail view; virtualized filmstrip; live folder refresh; track
grouping and switching; thumbnail and preview generation through a priority
job queue, content-addressed and cached; star ratings 1–5 and tags written to
XMP sidecars with optimistic updates and rollback; keyboard shortcuts for
culling; filter chips; reveal-in-Finder across multiple folders in one pass;
macOS native share sheet; light/dark theme; first-run welcome flow.

**Deliberate design limits:** RAW files are not demosaiced. Qeepa extracts the
JPEG preview already embedded in each RAW and renders that, so image fidelity
is bounded by what the camera embedded. Folders are scanned on visit and on
interval, not watched continuously. Qeepa never deletes a file.

**Degraded by platform:** sharing is macOS-only and falls back honestly to
reveal-in-folder on Windows and Linux.

**Built but not reachable — must not be presented as features:** the batch
import and SQLite library catalog, the settings screen, and the language
toggle all exist in code with no path to them through the UI.

**Shoot insights — confirmed shipped** (verified against the code on
2026-09-20; the feature audit missed this). `summarise()` in
`src/utils/photo-metadata.ts` returns a `MetadataSummary` carrying the most-used
aperture, shutter and ISO each with a percentage, a focal-length range, and a
gear list with per-item counts. `src/components/panel/folder-info-panel.tsx`
renders it, and `src/routes/gallery.tsx` mounts that panel as the gallery's
`gridInfoSlot`. It is reachable in normal use and may be described and
demonstrated.

**Filtering by export status — confirmed NOT shipped** (verified 2026-09-20).
The filters that exist are **Unrated** and **Tags**
(`galleryFilterUnrated`, `galleryFilterTags` in `src/localization/i18n.ts`,
surfaced through `src/components/gallery/filter-chips.tsx`). There is no
export-status or "delivered" filter anywhere in the codebase. The approved
landing copy for the photo-management row claims filtering "by rating and
export status"; the second half of that claim is not true today and must not
be demonstrated.

## Brand Commitments

- The product name is **Qeepa**. The `Keepa` spelling in the repository folder
  and some planning documents is legacy and is not used on the site.
- Typography is self-hosted and fixed: **Satoshi** for UI and body, **Erode**
  for display. Both are already in `public/fonts/`.
- The palette in `src/styles/global.css` is committed: white ground, warm
  neutral surfaces, a single peach accent, and three track colours for
  RAW / JPEG / AFPHOTO.
- The header wordmark is the name typeset in Erode. A logomark now exists
  alongside it: three dots in the RAW, JPG and EDIT track colours, RAW alone
  above JPG and EDIT — the app's own track dots turned into a mark. It is the
  favicon and the source for the app icon; the header wordmark on the page
  itself stays text-only. (Decided this session.)
- Voice is plain, warm, and unhyped. The landing copy approved in the brief
  doc is used verbatim.

## Product Principles

1. **The folder is the truth.** Never import, copy, move, or delete a
   photographer's files.
2. **Ratings belong to the photographer**, in formats other tools already
   read.
3. **The photographer decides.** Qeepa surfaces and sorts; it never culls on
   someone's behalf.
4. **Stay out of the way.** Thousands of RAW files must stay fluid to browse.
5. **Be a good citizen** in a workflow that already exists, rather than
   demanding to replace it.

## Accessibility & Inclusion

The Vercel Web Interface Guidelines are binding for this site (pinned by the
user this session). Specifically: every flow keyboard-operable with visible
`:focus-visible` rings; hit targets at least 24px, 44px on mobile; contrast
judged by APCA; `prefers-reduced-motion` honoured with a real reduced variant;
semantic HTML before ARIA; hierarchical headings with a skip link; status
never conveyed by colour alone. The app itself already reads the
reduced-motion preference once, app-wide.
